# 问题排查

排查属于分析类任务，**不必严格走开发规范**（不需要先建分支、不需要汇报模板），但有以下硬约束。

## 硬约束

1. **默认只读**：排查阶段不修改任何文件，不执行写操作、不改配置、不改数据、不执行 DDL/DML。
2. **先给根因分析，等用户确认后再改代码。** 即使修复方案很明显，也不要直接动手。
3. 用户确认修复后，才回到 AGENTS.md 的开发规范：检查 Git 分支与工作区、不在 master 修改、最小修改、给出 Commit 备注等。
4. 不假装验证：没有实际复现或运行过的，不能说"已验证"，要写明是静态分析得出的结论。
5. 只读查询也要谨慎：查生产库、生产日志、第三方接口前先确认用户允许；不输出敏感信息（密码、Token、密钥）。

## 排查流程

1. **明确现象**：报错信息、出现时间、影响范围（所有用户 / 特定用户 / 特定数据）、是必现还是偶发、最近是否有发布或配置变更。信息不足时，先列出最关键的 1~3 个问题询问用户，不要猜。
2. **定位入口**：根据接口路径、报错类名、日志关键字，找到入口 Controller / 方法。涉及具体项目时，用 skill `project-map` 确认是哪个项目、哪些模块。
3. **沿调用链追踪**：Controller → Service → Mapper/SQL → 外部调用（Feign、Redis、MQ、第三方）。跨服务时逐个项目确认真实实现，不凭印象推断下游行为；特别注意历史被注释掉的入口，以当前未注释代码为准。
4. **提出假设并逐个验证**：列出可能原因，每个假设用代码、日志、配置、数据结构中的证据去证实或排除；证据不足的保持"待确认"，不要写成结论。
5. **确认根因**：说明"为什么会出现这个现象"，而不只是"哪行代码有问题"。
6. **设计最小修复方案**，评估影响范围和风险，然后停下来等用户确认。

## 常见排查方向（按需检查，不必全部罗列）

- 空指针 / 类型转换 / 集合为空 / 边界值
- SQL：参数是否对应、逻辑删除条件是否遗漏、索引、分库分表路由（ShardingSphere）
- 事务：是否生效（自调用、异常被吞、非 public 方法）、事务边界是否合理
- 并发与幂等：重复提交、重复回调、缓存与数据库不一致
- 配置：Nacos 配置项缺失或环境不一致、开关未打开
- 跨服务：Feign 超时/降级返回、字段不兼容、服务版本不一致
- 回调类问题：签名校验、重试机制、供应商返回格式
- 数据问题：脏数据、历史数据与新逻辑不兼容

## 输出格式（对话中直接给出）

```text
## 现象
（用户描述的问题，一两句话）

## 根因
（为什么会发生；区分"已证实"与"推测，待确认"）

## 证据
- 文件路径:行号 —— 说明
- 日志/数据/配置 —— 说明

## 修复方案
- 方案 A（推荐）：改哪里、怎么改、为什么
- 方案 B（可选）：…
- 影响范围与风险：涉及的接口、调用方、数据、是否需要执行 SQL / 改配置

## 需要你确认
- 是否按方案 A 修复？
- （如有）需要补充的信息 / 需要你在生产环境查证的内容
```

内容要精炼：能一句话说清的不写成段落；没有的小节直接省略，不要为了凑格式而填充。

## 用户确认之后

1. 回到 AGENTS.md 开发规范：检查 Git 状态与分支，按规则处理分支。
2. 只做修复所需的最小修改，不顺手重构；发现的其他无关问题只提醒，不修改。
3. 按 skill `java-backend-dev` 等对应技术栈规范做静态检查。
4. 按 AGENTS.md 的最终汇报格式收尾，并推荐 Commit 备注。
