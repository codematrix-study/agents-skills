# 需求分析

需求分析属于分析类任务：**只读代码、只在对话中给出结果**，不修改任何文件，不生成 md/文档文件，不创建分支。
用户确认方案并要求开发后，再回到 AGENTS.md 的开发规范执行。

## 流程

1. **理解需求**：复述需求的目标、触发场景、涉及角色。需求有歧义、缺关键信息、或与现有行为可能冲突时，先列出问题，**不要擅自选一种理解往下做**。
2. **定位涉及项目**：用 skill `project-map` 判断涉及哪些项目（后端、前端、移动端），以及它们的上下游关系；不确定的项目逐个读代码确认。
3. **阅读现有实现**：找到相关的入口、业务逻辑、表结构、前端页面，弄清楚现在是怎么做的，不凭印象假设。注意历史注释掉的代码，以当前生效的入口为准。
4. **梳理影响面**：
   - 接口：新增还是修改？修改已有接口行为时，调用方（前端、其他服务的 Feign、开放平台）是否受影响，是否兼容
   - 数据库：是否需要新增表、字段、索引；存量数据如何处理
   - 配置：是否需要 Nacos 配置、开关、枚举值
   - 前端：涉及哪些页面和组件，是否多端都要改（PC、钉钉、移动端）
   - 跨服务：调用链上有哪些服务要联动
   - 历史兼容与灰度：旧数据、旧版本客户端
5. **设计方案**：在遵循"最小修改"和复用现有代码的前提下给出方案；有多种可行路径时给出 2 个以内的对比，说明取舍并给出推荐。
6. **识别风险**：事务与一致性、并发与幂等、性能（大表、批量）、权限与安全、回滚方案。
7. **列出待确认问题**，等用户答复后再进入开发。

## 输出格式（直接在对话中给出）

```text
## 需求理解
（目标、场景、边界；一两句话说清）

## 涉及项目与现状
| 项目 | 现有实现位置 | 本次是否改动 |
|---|---|---|

## 改动方案
（按项目分点：改什么、怎么改。说明为什么选这个方案）
- 备选方案及未选原因（如有）

## 影响面
- 接口 / 兼容性：
- 数据库（表、字段、存量数据）：
- 配置：
- 前端：
- 跨服务联动：

## 需要执行的 SQL
（只写 SQL 草案，不执行；没有则省略）

## 发布与联动顺序
（多服务改动时，先后顺序与依赖；单服务则省略）

## 风险与注意事项
-

## 需要你确认
1.
2.
```

没有内容的小节直接省略。简单需求（单项目、小改动）用几句话给出方案即可，不要套满整个模板。

## 注意

- 不确定的业务规则不要猜，先读代码和文档，仍无法确定就列入"需要你确认"。
- 方案里不引入新依赖、新框架、新架构，除非需求确实无法在现有体系内实现，并说明理由。
- 涉及数据库结构变更时，同时参考 skill `db-sql-safety`；涉及接口改动，参考 skill `java-backend-dev` 的"修改接口时"一节。
- 估算工作量时只给范围和主要不确定因素，不做精确承诺。
- 用户随后说"开始做"时：按 AGENTS.md 检查 Git 分支与工作区，需要新分支时先询问分支名，再进入最小修改开发。
