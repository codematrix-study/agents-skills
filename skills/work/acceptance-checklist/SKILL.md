# 验收单

本 skill 是 `bug-investigation` / `requirement-analysis` 之后的收尾环节：改动已经完成，把"改了什么、测什么、还可能波及什么"整理成一份给人看的验收单。读者是**用户本人和测试同事**，所以写法要让不读代码的人也能照着测。

## 硬约束

1. **只在用户明确说“验收”时输出**，不在开发完成后自动输出，不顺手附带。验收单在 AGENTS.md 第 7 章最终汇报之后输出，不重复文件列表、分支、Commit 备注。
2. **只读**：不修改任何文件，不生成文档文件，不执行构建/测试/启动，不执行 SQL，不提交、不推送。
3. **事实来自实际检索，不凭对话回忆**：改动范围来自 `git` 命令，影响面来自 `rg` 搜索调用关系。检索不到的不要编。
4. **区分证据等级**：每条影响面标注 `已证实`（代码里能搜到引用/调用）或 `推测待确认`（逻辑上可能但没找到直接证据）。不要把推测写成结论。
5. **不夸大验证状态**：没编译、没运行就写明"未执行编译/运行验证，仅静态分析"。
6. 不输出密码、Token、密钥、连接串等敏感信息。
7. 验收过程中发现与本次任务无关的问题，只在"注意事项"提一句，不修改。

## 流程

### 1. 确定验收范围（以 git 为准，范围可灵活选择）

验收范围有四种，**以用户指定为准，不要擅自换成别的**。范围按项目分别确定，多个项目可以各用各的范围。

| 范围 | 用户常见说法 | 取改动的方式 |
|---|---|---|
| A. 当前未提交改动 | "验收当前改动"、"验收现在改的" | `git diff HEAD --stat`（含已暂存和未暂存）；新增的未跟踪文件另用 `git ls-files --others --exclude-standard` 补充 |
| B. 某一次或某几次提交 | "验收最近一次提交"、"验收 abc123"、"验收 abc123..def456" | 单次：`git show <sha> --stat`，细节 `git diff <sha>^ <sha> -- <文件>`；区间：`git diff <起点> <终点> --stat`，并用 `git log --oneline` 确认包含哪些提交；merge 提交需先和用户确认看哪一侧 |
| C. 当前分支相对基线 | "验收这个分支"、"验收整个分支的改动" | `git diff <基线>...HEAD --stat`，并用 `git log <基线>..HEAD --oneline` 列出提交；基线分支**先问用户**（通常是 master），不要猜 |
| D. 分支已提交 + 当前未提交 | "验收这个分支，包括还没提交的" | 同时取 C 和 A，合并去重后展示 |

**用户没有指定范围时**，先对每个项目执行（路径见 skill `project-map`，命令按当前环境的语法）：

- `git branch --show-current`
- `git status --short`
- `git log --oneline -n 5`

然后判断：

- 有与本次任务相关的未提交改动，且没有明显的分支提交 → 默认用 **A**，并在验收概要里写明"范围：当前未提交改动"。
- 工作区干净 → 不要猜，问用户选哪种：最近一次提交 / 指定提交 / 整个分支相对基线。
- 既有未提交改动，又有分支上的提交，无法判断重点 → 问用户用 A、C 还是 D。

命令使用 PowerShell 语法，路径、分支名、提交号、搜索词用单引号包裹，例如：

```text
git diff 'master...HEAD' --stat
git show 'abc123' --stat
git diff 'abc123^' 'abc123' -- 'src/xxx.java'
```

通用要求：

- 范围必须写进验收单的"验收概要"，让读者清楚这份单子覆盖的是什么。
- 只列**与本次任务相关**的改动。范围内混入与本次任务无关的文件或提交时，不纳入验收单，在"注意事项"里提醒。
- 没有改动的项目不列；每个项目都要写明所在分支。
- 范围 B、C 的影响面检索基于**当前工作区代码**。若目标提交不在当前分支（`git branch --contains <sha>` 查不到），或之后又有改动覆盖了同一处，要在注意事项中说明"影响面基于当前代码，可能与该提交时不完全一致"。**不要为了检索去切换分支或 checkout。**

### 2. 提炼改动的代码模块

按"项目 → 模块 → 类/页面 → 方法"整理，每项一句话说明**改了什么、为什么改**。不贴代码、不贴 diff。

- 后端模块用 Maven 模块名（`*-web`、`*-core`、`*-dal`、`*-api` 等）。
- 前端用页面/组件路径。
- 改了 `*-api`（Feign 契约）、DTO/VO、Mapper XML、配置、枚举的，单独点出，因为它们的波及面更大。

### 3. 找出需要测试的接口

目标：测试同事拿到就知道**测哪些入口、每个入口测什么**。

- **直接改动的接口**：diff 中被改的 Controller 方法，列出。
- **间接触达的接口**：被改动的是 Service / Mapper / 工具类 / Feign 实现时，用 `rg` 沿调用链向上找到所有入口接口，列出。
- **非 HTTP 入口**同样要列：定时任务、MQ 消费、第三方回调、前端页面操作（写页面路径和操作入口）。
- 每个入口写：所属项目、HTTP 方法 + 路径（或入口名）、测试要点。**不写请求参数示例和预期返回体**，只写要点。

测试要点写法：每个入口 1~3 条，用一句话说清"测什么场景、关注什么结果"，例如"重复提交同一订单，只生成一条记录"。按任务类型补充：

- **bug 修复**：必须包含原问题的复现场景（修复后应不再出现），以及一个正常路径回归。
- **新需求**：包含新功能的主流程、关键边界（空值、超限、无权限）、与旧逻辑的兼容。
- **修改已有接口行为**：包含旧参数/旧客户端是否仍然可用。
- 涉及事务、幂等、并发、权限的改动，对应补一条。

### 4. 分析本次范围外的影响面

目标：找出"没直接改、但可能被连带影响"的接口和业务。

做法：对每个被改动的方法、类、Mapper、表、配置项、枚举、Feign 契约，用 `rg` 搜索其**他引用方**，排除第 3 步已列的入口，剩下的就是潜在影响。

按以下维度逐项检查（按需，不必全部罗列）：

- 共用的方法 / 工具类 / 公共组件，还有谁在调用
- 同一张表、同一个 Mapper 方法，其他业务的读写
- Feign 契约变更，其他服务里的调用方（跨项目逐个确认，参考 `project-map` 的常见跨项目链路）
- 前端其他页面或其他端（PC、钉钉、移动端）是否调用了同一接口
- 配置项、开关、枚举值、字典，还有谁在读
- 缓存 key、MQ topic、定时任务是否共用
- 事务边界、并发、幂等的变化是否波及其他流程
- 历史数据、旧版本客户端与新逻辑的兼容

每条影响面写：**影响对象 → 为什么受影响（共用了什么）→ 建议回归点 → 证据等级**。按风险从高到低排序，只保留有依据的，一般不超过 8 条；没有找到的维度不要凑数。

### 5. 测试前置与状态

- 测试前必须先做的事：需执行的 SQL、需添加的配置、多服务的发布顺序。只列出并指向最终汇报里的"需要执行的sql"，不在此处重写 SQL，也不执行。
- 验证状态：如实写本次做过哪些验证、哪些没做。

## 输出格式（直接在对话中给出）

```text
## 验收概要
（一两句话：这是 bug 修复还是新需求，解决了什么 / 实现了什么）
- 验收范围：按项目写明，如"项目 A（分支 x）：当前未提交改动；项目 B（分支 y）：提交 abc123"

## 改动的代码模块
| 项目（分支） | 模块 / 类 / 页面 | 改动说明 |
|---|---|---|

## 需要测试的接口
| 项目 | 入口（方法 + 路径 / 页面 / 任务） | 类型 | 测试要点 |
|---|---|---|---|
（类型：直接改动 / 间接触达）

## 可能影响的范围外接口与业务
| 影响对象 | 为什么受影响 | 建议回归点 | 依据 |
|---|---|---|---|
（依据：已证实 / 推测待确认）

## 测试前置
- 需先执行的 SQL / 配置 / 发布顺序（详见最终汇报）

## 验证状态
- 已做：
- 未做：

## 注意事项
- 与本次无关但发现的问题、工作区里无关的未提交修改等

## 需要你确认
- 推测待确认项中，需要你判断的内容
```

没有内容的小节直接省略。简单改动（单项目、单接口）压缩成几句话加一个小表格，不要套满整个模板。

## 注意

- 用户说"验收"但在可确定的范围内没有任何改动时，先说明没有可验收的改动，询问要验收哪个项目、分支或提交，不要编造内容。
- 可以参考此前排查/需求分析阶段给出的影响范围，但**必须用实际 diff 和检索结果校正**，以最终代码为准。
- 影响面检索量很大时，先用 `rg` 加目录和文件类型限定，只读命中处附近的片段，避免占满上下文。
