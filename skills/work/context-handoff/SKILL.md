# 上下文压缩与交接

## 先说明边界

- 本 skill **不能自己压缩上下文**，压缩由 Codex 的 `/compact` 或新开会话完成。
- 本 skill 做两件事：① 生成可靠的交接摘要，让压缩或换会话后不丢关键信息；② 约束平时的工作习惯，少占上下文。
- 触发后不要继续做开发任务，先输出摘要，并提示用户下一步怎么用。

## 一、生成交接摘要

### 原则

1. **只写事实，不凭记忆**：改动文件和分支状态必须实际执行 `git status`、`git diff --stat`、`git branch --show-current` 获取，不要凭对话回忆。涉及多个项目时，逐个项目执行（项目路径见 skill `project-map`），没有改动的项目不列。
2. **区分三种状态**：已证实 / 推测待确认 / 已排除。不要把推测写成结论。
3. **用引用代替粘贴**：用 `文件路径:行号` 指代代码和日志，不贴大段代码、完整日志或完整 diff。
4. **写"为什么"**：关键决策要带原因，否则新会话会重新讨论一遍。
5. **不含敏感信息**：不写密码、Token、密钥、数据库连接串。
6. **只留对后续有用的**：已经走不通的排查过程、重复的试错只留一句"已排除 X，原因 Y"。
7. **长度控制**：能用 300~600 字讲清就不要更长；信息多时用列表，不写长段落。

### 输出格式

```text
## 任务目标
（一两句话：要解决什么问题 / 实现什么需求）

## 当前进度
- 已完成：
- 进行中：
- 未开始：

## 涉及项目与分支
| 项目 | Git 分支 | 工作区状态 |
|---|---|---|
（未提交修改、是否在 master 要如实写；没有改动的项目不列）

## 修改文件
- 路径 —— 一句话说明改了什么
（来自 git diff --stat，不要凭记忆）

## 关键结论与决策
- 结论/决策 —— 原因（标注：已证实 / 推测待确认）

## 已排除
- 排除了什么 —— 为什么

## 待确认的问题
- 需要用户回答或决定的事项

## 需要执行的 SQL / 配置变更
（只列待执行项；没有则省略）

## 下一步
1.
2.

## 关键位置索引
- 文件路径:行号 —— 作用
```

没有内容的小节直接省略。

### 输出后提示用户

摘要给出后，用一两句话说明用法，例如：

- 想在当前会话继续：执行 `/compact`，并把上面摘要中的"当前进度、关键结论、下一步"作为保留重点。
- 想换新会话：把摘要整体粘贴到新会话开头，并说明"基于上面的交接摘要继续"。新会话开头应先让 Codex 重新检查 `git status`，不要直接信任摘要中的工作区状态。

## 二、平时节省上下文的习惯

在任何任务中都遵循（不需要等用户说"压缩"）：

1. **先定位再读取**：用 `rg` 搜索关键字定位文件和行号，再读相关片段，不整文件读取大文件。
2. **按范围读**：已知位置时只读目标方法及其前后少量上下文；大文件分段读。
3. **日志只取关键段**：错误堆栈取根因附近，不把整份日志塞进对话。
4. **不重复贴内容**：改动汇报用文件路径和一句话，不把改过的代码再完整贴一遍；用户要看细节时再给。
5. **搜索结果先收窄**：`rg` 加文件类型或目录限定；输出过长时先看数量或文件列表。
6. **阶段性小结**：多步任务每完成一个阶段，用一两句话固化结论，后续引用结论而不是重读原文。
7. **不引入无关文件**：只读与当前任务相关的项目和模块，不顺手浏览整个仓库。

## 三、何时主动建议压缩或换会话

出现以下情况时，主动用一句话建议用户："当前对话较长，要不要我先生成一份交接摘要？"

- 同一会话已经跨了多个项目、多轮改动，需要回头确认状态
- 已经读过大量文件或长日志，后续还要继续
- 任务阶段切换，例如从排查转入开发，或从需求分析转入实现
- 发现自己开始遗漏或重复前面已经确认过的内容

不要频繁打断：同一会话建议一次即可，用户拒绝后不再重复。
